# Quality and readiness gates

## Gate 0 — Research and inspiration (when applicable)
- Relevant alternatives and adjacent products were considered before the first visual concept.
- At least the key workflow patterns, drawbacks and potential improvements were discussed, not only visual styling.
- Claims are sourced and qualified; unavailable research is declared rather than fabricated.
- Borrowed conventions are adapted to the user’s requirements without copying protected creative assets.

## Gate 1 — Concept direction
- User recognizes the intended purpose and visual direction, or unresolved differences are visible.
- Visuals are labeled as exploratory and contain no invented authoritative data.
- Major rejected directions are preserved as rejected.

## Gate 2 — Workflow and design
- Primary user journey is explicit, with actor, starting state, action, resulting state and exit.
- Critical variants and exceptions have been considered (interruptions, errors, cancellation, lack of permission).
- Interface controls have defined behaviors; appearance approval is not mistaken for workflow approval.
- Contradictions and open high-impact questions are visible.

## Gate 3 — Document consistency
- Requirements, design, architecture (if present) and stages agree on names, scope and capabilities.
- Every stage traces to requirements and has testable acceptance criteria.
- No invented security behavior, source evidence, existing feature or test result.
- Small projects are not burdened with unnecessary artifacts.

## Gate 4 — Ready for a development agent
- The first stage can be completed and tested in isolation with clear prerequisites and excluded changes.
- References and source materials are obtainable by the implementation agent, or missing access is called out.
- User knows exactly what to approve for implementation; design sign-off is separate.
- Agent response must include evidence, tests attempted/results, changes made, blockers and deviations.

## Gate 5 — Stage review
- Evidence supports the claimed status; distinguish reported from independently verified.
- Accepted scope is preserved. Follow-on work includes only justified changes.
- Unresolved blocking issues prevent an unsupported readiness claim.
